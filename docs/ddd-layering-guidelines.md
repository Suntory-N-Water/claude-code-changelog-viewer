# Functional DDD 層分類ガイドライン

Functional DDD を採用するプロジェクトで、domain / usecase / infrastructure / entry point の責務分担を判断するための共通指針。
特定プロジェクトへの実装移植ではなく、判断の語彙と手順を共有することを目的とする。

## 前提整理

層分類は対象プロジェクトの前提によって結論が変わる。判断前に少なくとも次を言語化しておく。

| 項目 | 内容 |
|------|------|
| 入力 | CLI 引数 / HTTP request / queue message / Markdown / JSON / DB record / 外部 API response 等 |
| 出力 | UI response / 通知 / 保存 JSON / DB record / 生成ファイル / 外部 API request 等 |
| 利用者 | エンドユーザー / 運用者 / 他アプリ / 後続バッチ / AI モデル等 |
| 業務上の不変条件・ポリシー | 分類 / 重複判定 / 状態遷移 / 優先順位 / 権限制御 / 通知可否 / 公開可否等。ドメインエキスパートが説明できる判断 |
| 差し替え候補となる技術依存 | 保存先 / 外部 API / ファイル形式 / SDK / AI provider / ログ基盤等 |

前提を確認せずに「これは domain」と決めない。

## 層と責務

呼称とディレクトリの対応:

| 層 | ディレクトリ | 役割 |
|----|------------|------|
| ドメイン層 | `domain/` | 業務上の不変条件・分類・状態遷移を表現する型と純粋関数 |
| ユースケース層 | `usecase/` | ユースケースの進行管理。port の呼び出し順、トランザクション境界 |
| インフラ層 | `infrastructure/` | 外部形式・技術基盤・副作用。port 実装、シリアライザ |
| エントリポイント | プロジェクトの慣習による(`routes/`, `cli/`, `queue/` 等) | 実行環境との接続のみ |

### domain

domain には、業務上の不変条件・分類・優先順位・状態遷移を置く。

- 純粋関数であることは domain の十分条件ではない。**入力形式や保存形式を変えても残る判断か**を問う。
- 「入力形式に依存しないか」だけで usecase 層との区別がつかない場合は **業務ルール(ドメインエキスパートが説明できる判断)か、ユースケースの進行管理か**を追加で問う。
- Markdown / CSV / 帳票のように技術形式に見えても、利用者が業務上その形式を概念として扱うなら domain に含まれうる。
- domain は副作用を持たない(`await fetch`、`fs`、`db` を import しない)。
- port (interface) の宣言は domain に置くことができる(リポジトリ・通知器など、ドメインの言葉で語る境界)。実装は infrastructure に置く。

ドメインモデル貧血症を避けるため、ふるまいはまず値オブジェクト・エンティティに相当する型に持たせる。複数オブジェクトを横断するなど、特定の型に持たせると不自然なものだけドメインサービスに切り出す。

### usecase

usecase には、domain の判断と infrastructure の外部能力を組み合わせてユースケースを完了させる進行管理を置く。

- 置くもの: どの port をどの順で呼ぶか、retry、既存結果の再利用、保存タイミング、**トランザクション境界**。
- 1 トランザクションで変更する集約は原則 1 つ。複数集約をまたぐ変更が必要なら結果整合性を検討する。
- 置いてはいけないもの:
  - 業務ルール(分類・重複判定・状態遷移)を usecase 内で if 分岐して書くこと。domain 関数に委譲する。
  - HTTP / argv / env / 形式変換のような実行環境固有の処理。
- port は引数で受け取る(直接 import しない)。テストでの差し替えとレイヤ依存方向の制御のため。

複数オブジェクトを横断する業務ルール(重複判定など)は、usecase が repository でデータを揃えて domain 関数に引数として渡すパターンで実現する。domain 関数自身が repository を呼ばない。

### infrastructure

infrastructure には、外部形式・技術基盤・副作用を置く。

- 含まれるもの: DB / filesystem / HTTP / SDK / AI provider / Markdown parser / JSON schema / snake_case ↔ camelCase 変換 / Date 文字列変換 / port 実装。
- domain の値オブジェクトやファクトリを呼んで domain object を再構築することは許容する。
- 業務ルールを adapter の内部事情として隠さない。policy として説明したい判断は domain に置く。
- domain 型 ↔ 外部 JSON 契約の変換(snake_case 整形、スキーマ整形、branded type の解除など)は infrastructure のシリアライザに集約する。

### entry point

entry point は実行環境への接続のみを担う。

- 置くもの: argv / env / request / response / exit code / wiring(port の組み立て)/ 表示ログ。
- 置いてはいけないもの: 業務ルール、domain 型のフィールドへ直接アクセスする変換処理。
- 実行環境を切り替えた(CLI → HTTP 等)ときに業務ルールを移植する必要があるなら、それは entry point に漏れている。

## モデリング判断

### 値オブジェクトとエンティティ

判定基準は **同一性 vs 等価性 / ライフサイクル**。

- 値オブジェクト相当: 同じフィールド値を持つ 2 つは同一とみなす。不変として扱い、変更時は新しい値を返す。
- エンティティ相当: ID フィールドで同一性を判定する。ライフサイクル(生成・更新・削除)を持つ。フィールド更新時もスプレッドで新オブジェクトを返す。

境界事例は **業務上ライフサイクル・履歴・連続性を持たせる必要があるか**を問う。同じ概念でも文脈次第で扱いが変わる(典型例: タイヤは一般ドライバには値オブジェクト、製造工場ではエンティティ)。

不変性は `readonly` だけでは保証されない:
- 配列要素の mutation (`ReadonlyArray<T>` を使う)
- ネストオブジェクト(再帰的に `Readonly`)
- 同じ参照を複数の集約が共有する場合(生成時にコピーする)

### 集約境界

**変更の単位** = 集約。1 トランザクションで一緒に変更すべき範囲を 1 つの集約にする。

- 外部からの操作はすべて集約ルートを経由する。集約境界内のオブジェクトを直接公開しない(不変条件を保つため)。
- 他の集約は ID で参照する(集約間の直接参照は持たない)。
- 1 つのユースケースで変更する集約は原則 1 つ。

### ファクトリ

複雑な生成知識をまとめる関数として用意する。

- 作る条件: 採番が伴う、複数フィールドの検証が必要、複数オブジェクトの組み立てが必要、生成失敗のハンドリングが必要。
- 作らない条件: フィールドをそのまま詰めるだけ(インラインで十分)。
- 配置: domain。生成知識は業務ルールの一部であり、usecase / infrastructure に散らさない。

### リポジトリ

集約単位で 1 つ用意する。

- 命名はドメインの言葉で表現する(`saveAnalysis`, `findChangelogByKey`, `loadNotificationState` 等)。`executeSql`, `readJsonFile` のような技術語彙を usecase に公開しない。
- domain policy(重複判定、状態遷移、分類、優先順位付け)を repository 実装に押し込まない。
- 集約をまたぐ複雑なクエリ(集計・一覧表示など)は、集約 repository に押し込まずに**リードモデル**として infrastructure に書いてよい。ただし**書き込みは必ず集約 repository 経由**。
- port を domain と usecase のどちらに宣言するかはプロジェクト方針で決める。集約に直結する repository / notifier は domain、副作用境界の外部 API クライアントは usecase に置くなどの使い分けがありうる。

### ドメインサービス

最後の手段として位置付ける。

- 作る前に、まず値オブジェクトかエンティティ相当の型(その型を引数に取る関数)にふるまいを持たせられないか検討する。
- 複数オブジェクトを横断するなど、単一の型に持たせると不自然な業務ルールに限って独立した純粋関数として切り出す。
- Functional DDD では状態を持たない純粋関数として実装する。OOP DDD のように repository を呼ばない(domain は副作用を持たない)。

ドメインサービスの濫用はドメインモデル貧血症を招く。

### 仕様パターン

評価基準を満たすかを判定するオブジェクト(関数)として切り出す。

- 用途: 複雑な評価手順(複数フィールドの組み合わせ判定など)をオブジェクトのメソッドに埋もれさせず、ドメインの語彙で切り出す。
- repository と組み合わせる場合、重要な評価ルールが repository 実装に漏れるのを防げる。
- 単純な述語(`isActive` 等)は型を引数に取る関数で十分。仕様パターンは複数条件を組み合わせる必要が出てきたときに導入する。

## 横断的な判断軸

### DTO の置き場所

「**誰との契約か**」で決める。

| DTO の種類 | 置き場所 | 理由 |
|-----------|---------|------|
| 他アプリも読む保存 JSON 契約 | shared / contract package | 公開契約。複数プロジェクトが依存する |
| そのアプリ内部だけの外部 API response | infrastructure | provider / SDK の応答形式に依存する |
| ユースケースの入力・出力 | usecase | ユースケース境界の入れ物。業務ルールではない |
| domain snapshot | domain | 不変条件・状態遷移の対象 |

shared package には **他プロジェクトが読むことを約束した契約だけ**を置く。内部 provider 応答 schema を出さない。

### port の作成条件

port は依存逆転のために置く:

```
usecase → port (interface) ← infrastructure の実装
```

- domain は port すら呼ばない(純粋関数として引数を受け取り値を返すだけ)。port を呼ぶのは usecase だけ。
- 新設の理由が次のいずれかで説明できなければ作らない:
  1. テストで差し替えたい
  2. 外部 provider を usecase から隠したい
  3. 副作用境界を usecase から遠ざけたい
- 適切な対象: 外部 API / DB / filesystem / AI provider / queue / mail / 検索基盤。
- 作らない: 純粋な形式変換、業務ルール、単なる map 処理。薄い interface は禁止。

### helper の追加条件

helper は原則として追加しない。次のいずれかを満たすときだけ追加する:

- 2 箇所以上から呼ばれる
- 分岐・検証・副作用境界がありインラインでは明確に読みにくい
- 既存の同種パターンに揃える必要がある

例外: 外部契約変換や状態遷移のように**名前が責務を説明する**ものは、単一 call site でも関数化を許容する。

1 箇所からしか呼ばれない整形・map・変換は call site にインライン。

### readonly の使い分け

`readonly` は層分類ではなく **mutation 意図** で判断する。

付ける候補:
- domain の値オブジェクト / snapshot
- usecase input / output DTO
- 外部 JSON 契約 DTO
- port の input / result 型

付けない:
- ローカル accumulator
- 一時的に組み立てる mutable object

## アンチパターン

| 兆候 | 何が壊れるか | 直し方 |
|------|------------|-------|
| 純粋関数だから domain と即断 | DTO / provider 応答まで domain に混入 | 「入力形式に依存しないか」「誰との契約か」を再確認 |
| 外部依存だから port と即断 | 薄い interface が量産される | 「差し替え / 隠蔽 / 依存制御」のいずれかで説明できるか |
| domain 型がデータ保持専用 | ドメインモデル貧血症 | まず値オブジェクト・エンティティ相当の型にふるまいを持たせる |
| usecase で `if (count >= 3)` のような業務ルール分岐 | domain ルールの漏れ | domain 関数に委譲 |
| entry point で `obj.fieldA` → `field_a` 変換 | infrastructure の仕事が漏れる | infrastructure のシリアライザに移す |
| repository 実装の中で重複判定 | domain policy が repository に混入 | domain 関数に出して usecase から呼ぶ |
| shared package に provider 応答 schema | 公開範囲ミス | 内部 schema は infrastructure に閉じ込める |
| `port.executeSql(sql)` | 技術語彙が usecase に漏れる | `port.saveAnalysis(analysis)` のようにドメインの言葉に置き換え |
| domain で `await fetch(...)` | domain が副作用を持つ | port を usecase 経由で呼ぶ |
| 1 つのユースケースで複数集約を同一トランザクションで保存 | ロック競合、整合性破綻 | 集約境界を見直す、または結果整合性へ |
| ドメインサービスを早期に量産 | ロジックが点在し貧血症を招く | まず型にふるまいを持たせる。横断ルールに限り切り出す |
