# ドキュメント検索を D1 の FTS5 に置き換える

ドキュメント検索には Python 実装(BM25 と spaCy)と TypeScript 実装(正規表現)の2つがある。
Python 実装はサブプロセス起動(`spawn`)を前提としており、Workers ランタイムでは動かせない。
そこで両方を D1 の FTS5 に置き換える。

現行の検索の動作は経路ごとに異なる。

| 経路 | 検索の流れ | 検索語 |
|---|---|---|
| 設定リファレンス生成 | TypeScript の正規表現検索 → 抜粋0件の項目だけ Python の BM25 | 設定キーの末端名 |
| CHANGELOG 推論 | 最初から Python の BM25 のみ。TypeScript 検索を経由しない | CHANGELOG の箇条書き1行 |

設定リファレンス生成の1段目にあたる「完全一致」の実体は3段のフォールバックである。

1. 本文に検索語がバッククォートで囲まれた形で出現するファイルをリテラル一致で探す。1〜50件ならこれで確定
2. 0件か51件以上なら、囲みを外して大文字小文字を無視した部分一致(単語境界なし)で探し直す。1〜50件ならこれで確定
3. それも外れたら 2 の結果を先頭50件で打ち切る

呼び出し側は正規化前後に同じ文字列を渡しているため、実運用では 2 と 3 は同じ結果になる。

FTS5 では、この2段構え(バッククォート囲みの一致を先に評価し、0件のときだけ BM25 に落ちる)を1本の SQL の中で再現する。
どちらを採用するかの判断を呼び出し側に持たせると、2つの経路で挙動がずれてしまう。

## Considered Options

BM25 のスコアによる線引き(現行はファイル内最高スコア25点以上)は廃止し、件数の上限だけにする。理由は次の2つ。

- FTS5 の `bm25()` は k1 が 1.2 に固定されており(SQLite 本体でハードコード、変更不可)、Python 側のライブラリ(k1 = 1.5)とは値域が異なる。さらに FTS5 は値が小さいほど良い一致という逆向きの目盛りであり、25 という数字を移植できない
- 25 という値は「Gemini の無料枠の分あたりトークン上限を超えたので 18 から引き上げた」という経緯で決まったもので、根拠となる目盛りが失われる

## Consequences

- Worker 上では Python 実装に戻せない。そのため切り替え前に、現行実装と FTS5 の出力を突き合わせて検証する。合否は実際の出力を見てユーザーが判断する(事前の数値基準は置かない)。
- FTS5 は virtual table であり、virtual table を含むデータベースは export できない(ADR 0003 を参照)。
- スコアの線引きの代わりに件数の上限(3ファイル × 各3チャンク)で量を抑える。ただしチャンク自体の長さに上限はない(本番の `page_chunks` は平均1,123字・最大116,749字・2,000字超が830行)ため、件数だけでは出力量が決まらない。現行の Python 実装と同じく、チャンクを段落に割って先頭2段落と検索語を最も多く含む1段落だけに絞る。
- バッククォート囲みが当たった段のスコアは、同じ検索式の BM25 から借りる。リテラル一致は当落しか決められず、そのままではファイルの上位3件がパス名の昇順で決まってしまう。
