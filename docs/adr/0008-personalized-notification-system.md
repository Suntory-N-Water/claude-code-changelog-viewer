# ADR 0008: 通知パーソナライズ基盤の整備

## Status

Proposed

## Context

現在の通知システム(ADR 0005・0006 で構築したD1 + Queues 構成)は、新バージョンが検出されると全登録者に同一内容の通知を送信する。Claude Code は月に20件以上のリリースがあり、ユーザーごとに関心のある機能領域(MCP、Hooks、IDE/VSCode など)は異なるにもかかわらず、フィルタリングの仕組みがない。

通知をパーソナライズするには、各変更に付与される機能エリアタグの精度が前提条件になる。現状のタグ付けには構造的な問題があり、まずそこから解決する必要がある。

### 解決したい課題

- **タグ精度の問題**: 機能エリアタグは正規表現(第1段階)→ Gemini 補正(第2段階)の2段階で付与されているが、`settings?` パターンが「setting」を含む文脈全般にマッチするため、v2.1.113 では38件中10件に `Settings` タグが誤付与されている。Gemini は「補正が必要なものだけ返す」という指示のため正規表現の誤タグに引きずられやすく、ノイズが最終結果に残る
- **通知の均一性**: 全登録者が同一内容の通知を受け取る。MCP にしか興味のないユーザーが38件の変更を受け取る
- **Weekly モードの未実装**: D1 スキーマの `notification_settings.frequency` に `'IMM' | 'WEK'` が定義済みだが、consumer が `IMM` しかクエリしておらず `WEK` 登録者は通知を受け取れない

### 検討した選択肢

**タグ精度改善の方法:**

- A. 正規表現パターンを絞る(`setting` → `settings\.json` など文脈限定)
- B. 正規表現を削除し、Gemini に最初から分類させる
- C. 現状維持(精度が低いままパーソナライズは諦める)

**パーソナライズの粒度:**

- D. 機能エリア単位(MCP / Hooks / Skills など11カテゴリ)
- E. 変更タイプ単位(ADDED / CHANGED / IMPROVED / FIXED)
- F. パーソナライズなし(全件通知のまま)

### 各選択肢の評価

| 観点 | A(regex絞り込み) | B(regex削除) | C(現状維持) |
|------|-----------------|--------------|-------------|
| 実装コスト | 低 | 低 | なし |
| 精度改善効果 | 部分的 | 高い | なし |
| Geminiとの整合性 | ノイズ減少のみ | 二重処理を排除 | 不整合継続 |

| 観点 | D(機能エリア) | E(変更タイプ) | F(なし) |
|------|--------------|--------------|---------|
| ユーザー価値 | 高い | 中程度 | なし |
| タグ精度への依存 | 高い(前提条件) | 低い(既存分類が信頼できる) | なし |
| 表現の自然さ | 「MCPだけ知りたい」に合う | 「バグ修正は不要」に合う | — |

## Decision

**機能エリアタグの精度を正規表現削除とGeminiプロンプト定義の改善で高め、その精度を前提に機能エリア単位のパーソナライズ通知と Weekly ダイジェストを実装する。**

### 1. 正規表現タガーの削除

`apps/changelog-fetcher/src/parsers/feature-area-tagger.ts` の正規表現ルールを廃止し、Gemini への入力時に `feature_areas` を空配列で渡す。Gemini が文脈から直接分類することで、誤った先入観を排除する。

### 2. Gemini プロンプトの定義を具体化

タグ補正タスクの各カテゴリ定義に、**対象の明示と除外条件**を追加する。基準は公式ドキュメント(`docs/en/`)の対応ファイルに記載されている項目とする。

```
- Settings: settings.md および server-managed-settings.md に記載されている設定項目に
  直接関わる変更(settings.json のキー・スコープ設定・/config コマンド・CLAUDE.md の
  ロードロジック)。除外: キーボードショートカット・UI 表示・認証・モデル設定
- MCP: Model Context Protocol の接続・ツール呼び出し・サーバー管理に関わる変更
```

各カテゴリの除外条件は、公式ドキュメントの対応ファイルを参照して同様に定義する。

### 3. D1 スキーマに followed_areas を追加

`apps/notification-worker/src/db/schema.ts` の `notificationSettings` テーブルに機能エリアの購読設定を追加する。

```sql
ALTER TABLE notification_settings
  ADD COLUMN followed_areas TEXT NOT NULL DEFAULT '[]';
-- JSON 配列文字列として格納。例: '["MCP","Hooks","Skills"]'
-- 空配列 '[]' は全件通知を意味する(後方互換)
```

**設計の根拠**: 別テーブル(正規化)ではなく JSON カラムを採用する。consumer はすでに全チャンネルを取得して JS 側でループ処理しており、DB レベルでエリアフィルタする必要がないため。アプリ側では必ず `JSON.parse()` してから使用すること。

SQLite の `ALTER TABLE ADD COLUMN` は既存行に `DEFAULT '[]'` を適用するため、**既存登録者は移行スクリプト不要**で全件通知のまま維持される。

### 4. Consumer でのフィルタリング

`apps/notification-worker/src/queue/consumer.ts` で通知メッセージ生成時に `followed_areas` で変更をフィルタし、関連変更件数をサマリに含める。

```
"v2.1.113 リリース：あなたがフォローする MCP に2件の変更があります"
```

`followed_areas` が空配列の場合は現行と同様に全件通知する。

### 5. Weekly ダイジェスト実装

`notification-worker` に Cron Trigger を追加し、毎週月曜 9:00 JST に `WEK` 登録者へ前週のバージョンをまとめて配信する。

配信内容は **各バージョンの `summary` フィールド**(Gemini が生成済みの 1〜2 文の日本語要約)＋ バージョン番号 ＋ ページリンク。`followed_areas` が設定されている場合は関連変更件数を添える。Before/After/Benefit の全件は含めない。

## Consequences

### Positive

- 機能エリアに関心のあるユーザーが不要な通知を受け取らなくなる
- タグ精度向上により機能エリア別ページ(既存)の分類精度も改善される
- 既存 `frequency: 'WEK'` 登録者がはじめて通知を受け取れるようになる
- 正規表現の削除によりコードが簡素化される

### Negative

- 通知登録 UI に機能エリア選択を追加する必要がある
  - → 登録フォームに機能エリアのチェックボックスを追加し、`RequestSchema` に `followed_areas`(任意・デフォルト `[]`)を追加する
  - → 既存登録者は `followed_areas = '[]'`(全件通知)のまま自動移行される
  - → テスト通知に設定変更リンク(`/settings?token={token}`)を含め、登録後も変更できる導線を設ける。設定変更ルートは `/api/settings` として notification-worker に追加する
- Gemini の分類が変わるため、過去バージョンとの一貫性が失われる
  - → 既存 inferred JSON は再処理しない。新バージョンから順次適用する

### Risks

- Gemini の分類精度がプロンプト変更後に想定通り改善されない可能性
  - → 変更後に数バージョン分の出力を目視確認し、必要なら定義を追加調整する

## 決めていないこと

| 項目 | 決めない理由 | いつ決めるか |
|------|------------|------------|
| 登録 UI のデザイン(チェックボックス vs トグル等) | UX は実装時に判断すれば十分 | 着手時 |
| Weekly ダイジェストの配信曜日・時刻 | 利用者数が増えてから最適化 | 運用後 |
| 過去バージョンのタグ再処理 | スコープ外とし現時点では行わない | 必要になれば別ADRで判断 |
