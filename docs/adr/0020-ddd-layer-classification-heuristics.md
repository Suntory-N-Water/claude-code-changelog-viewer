# ADR 0020: DDD 層分類の判断ヒューリスティック

## Status

Accepted

## Context

ADR 0019 の実装作業（changelog-fetcher への DDD 適用）を進める中で、ある処理をドメイン層に置くべきかインフラ層に置くべきかの判断が難しい場面が繰り返し発生した。

具体的には `extractKeywordSetFromContent`（CHANGELOG 項目のテキストからバッククォート記法・大文字略語を抽出する処理）の置き場所が論点になった。「キーワード抽出」という言葉だけ聞くとドメイン的に見えるが、実際の処理内容はバッククォート記法（`` `keyword` ``）や大文字略語（`MCP`、`SDK` など）という Markdown フォーマットへの依存が本質であり、ドメイン知識ではなかった。

この判断を都度議論するのではなく、チームで共有できる実用的な基準として言語化する必要があった。判断基準は NotebookLM に登録した「ドメイン駆動設計入門.md」で裏付けを取った。

### 解決したい課題

- 「ドメイン層 / インフラ層」の分類判断が属人的になっており、実装のたびに迷いが生じる
- 「正規表現を使っているからインフラ」のような実装手段による誤分類が起きやすい
- 「業務ルール・不変条件」という DDD の定義が抽象的で、実務で即座に使いにくい

### 検討した選択肢

1. 「副作用の有無」で分類する（純粋関数 → ドメイン、I/O あり → インフラ）
2. 「ドメインの人が気にするか」で分類する
3. 「入力フォーマットを変えたら死ぬか」で分類する
4. 上記②③を組み合わせて使う

### 各選択肢の評価

| 観点 | ①副作用の有無 | ②ドメインの人が気にするか | ③フォーマット変更で死ぬか | ④②③の組み合わせ |
|------|-------------|--------------------------|--------------------------|----------------|
| 直感的か | 中。純粋関数でも形式依存はある | 高い | 高い | 高い |
| 誤分類を防げるか | 低。`extractKeywords` は純粋関数だがインフラ | 高い | 高い | 高い |
| グレーゾーンへの対応 | 弱い | 中。「気にするか」が曖昧な場合がある | 中。単独では不足することがある | 強い。2軸で補完できる |
| 説明しやすさ | 中 | 高い | 高い | 高い |

## Decision

**ドメイン層 / インフラ層の分類には「ドメインの人が気にするか」と「入力フォーマットを変えたら死ぬか」の2つのヒューリスティックを組み合わせて使う。**

### 1. ヒューリスティック①「ドメインの人が気にするか」

「ドメインの人」＝業務を知っているが技術実装を知らない人。changelog-fetcher であれば CHANGELOG を管理・活用する人。

```
「この変更は Added か Fixed か分類してほしい」
  → 管理する人が気にする判断            → ドメイン層

「バッククォートで囲まれた語を取り出してほしい」
  → 管理する人は知らない・関与しない    → インフラ層

「同じキーワードが重複していたら1つにしてほしい」
  → 「重複は意味がない」と言える業務ルール → ドメイン層
```

### 2. ヒューリスティック②「入力フォーマットを変えたら死ぬか」

Markdown をやめて JSON 入力にした場合：

```
classifyChangelogPrefix  → ロジックは同じ（Added は Added）     ✅ ドメイン層
extractKeywords          → バッククォートがないので全書き直し    ✅ インフラ層
parseChangelogEntries    → ## も - もないので全書き直し         ✅ インフラ層
KeywordSet の重複排除    → フォーマットに関係なく成立する       ✅ ドメイン層
```

### 3. 重要な気づき：分類は実装手段ではなく「何を判断しているか」で決まる

```ts
// ✅ ドメイン層 — 正規表現を使っていてもドメイン
// 「Added という業務分類を定義している」のが本質
export function classifyChangelogPrefix(content: ChangelogEntryContent): ChangelogPrefix {
  if (/^-\s*(Added|Adding|Add)\b/i.test(content)) return 'Added';
  if (/^-\s*(Fixed|Fix|Fixes)\b/i.test(content))  return 'Fixed';
  // ...
}

// ✅ インフラ層 — 正規表現だけでなく「Markdown の読み方を知っている」のが本質
// バッククォート記法・大文字略語という特定フォーマットへの依存
export function extractKeywords(entry: ChangelogEntry): KeywordSet {
  const backtick = [...content.matchAll(/`([^`]+)`/g)]; // Markdown 構文
  const upper    = [...content.matchAll(/\b([A-Z]{2,})\b/g)]; // テキスト慣習
  // ...
}
```

### 4. 判断フロー

```
[処理を評価する]
       │
       ▼
┌──────────────────────────────────┐
│ 業務を知る人が「こうしてほしい」  │
│ と言いそうな判断・ルールか？      │
└──────────────────────────────────┘
       │ YES                │ NO
       ▼                    ▼
┌──────────────┐    ┌──────────────────────────┐
│ 入力形式が   │    │ 外部システム・I/O・       │
│ 変わっても   │    │ フォーマットへの依存か？  │
│ 成立するか？ │    └──────────────────────────┘
└──────────────┘           │ YES         │ NO
   │ YES  │ NO             ▼             ▼
   ▼      ▼          [インフラ層]  [アプリケーション層]
[ドメイン] [インフラ]
```

## Consequences

### Positive

- 「正規表現を使っている＝インフラ」のような実装手段による誤分類を防げる
- 2つのヒューリスティックが補完し合うため、片方で判断が難しいケースを他方でカバーできる
- 具体例と照合できるため、新規参加者がすぐに使える

### Negative

- 2つのヒューリスティックが矛盾するグレーゾーンはまだ存在する
  - → そのときは「変更理由が業務の変化か、技術の変化か」を追加の問いとして使う
- 「ドメインの人」が誰かがプロジェクトによって異なる
  - → ADR 0019 や CLAUDE.md でプロジェクト固有の文脈を補足する

### Risks

- ヒューリスティックが一人歩きして機械的に適用され、本来の意図（ビジネスロジックの保護）を見失うリスク
  - → このルールは補助線であり、最終判断は「ドメイン駆動設計入門.md」の基準に戻って確認する
