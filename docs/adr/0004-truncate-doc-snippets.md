# ドキュメントのスニペットを検索側で切り詰める

公式ドキュメントのチャンク分割は空行だけを境界にしているため、空行を含まない Markdown テーブルは何行あっても1つのチャンクになる。
`env-vars.md` の `## Variables` はテーブル本体326行に空行がなく、実測で116,749文字の1チャンクになる。`settings.md` の `### Available settings` も同じ構造を持つ。
このチャンクは段落数1と判定されて全文がスニペットとして返る。git 履歴上の推論入力を走査すると、実際に64,520文字のスニペットが AI へのプロンプトに載っていた。
根本の原因はチャンク分割にあるが、そこを変えるとドキュメント検索用 D1 の全件再同期が必要になる。同期処理は本文のハッシュが一致するページをスキップするため、強制的に再同期する仕組みを別に作ることになる。
そこで検索側で1スニペットあたりの文字数に上限をかけ、改行の境界で切る。テーブルのヘッダー行はチャンクの先頭にあるので、末尾側を切ればヘッダーと先頭の数行が残る。

## Consequences

- テーブルは途中で切れる。AI は表の後半を見られなくなる。
- チャンク分割側の欠陥は残る。巨大なチャンクは FTS5 のインデックスに入ったままで、BM25 が使う平均文書長にも影響し続ける。
- 設定リファレンス生成は別実装の検索を使っているため、この変更の影響を受けない。
